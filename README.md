# Oaken — D&D Campaign Manager

> **Renamed (DL-176).** The app was called Campaign Ledger / D&D Ledger; it is now **Oaken**. Still using the old names on purpose: the Supabase buckets `ledger-uploads` and `ledger-temp` (override with `STORAGE_BUCKET_UPLOADS` / `STORAGE_BUCKET_TEMP`), the Vercel project and URL, and the GitHub repository. `LEDGER_QUOTA_*` variables still work when `OAKEN_QUOTA_*` are not set. The session cookie is now `__Host-oaken` (`oaken_session` locally), so everyone signs in once more after the update. Migration `0057_rename_to_oaken.sql` rewrites the old name in the tutorial campaign's text.

A browser-based app for running D&D campaigns online with your table: campaigns and
members, characters and factions, live battles, interactive maps, dice, and a 2024
rules reference. Flask + Postgres (Supabase) + Supabase Storage, deployed on Vercel.
It also runs locally.

## Features

- **Campaigns and accounts.** Self-registration, login, invitations and invite links. Each account has a basic
  profile at `/account` (display name, avatar, bio); the display name replaces the username in the sidebar, the
  username stays the login. Profiles are private to their owner for now and need no campaign. `/account` also
  changes the password (current password required; wrong guesses share the login throttle) and offers "sign out
  everywhere else"; both bump `users.session_version`, which ends every other session on its next request. An optional
  email address is confirmed with a signed 24-hour link sent over SMTP (`mailer.py`, any provider; settings in
  `.env.example`). A forgotten password is reset from the login page with a one-hour, single-use link sent to a
  *confirmed* address (an address no account has confirmed is told so on the page, and the mail throttles limit how fast addresses can be tried); a reset ends every session and
  mails the owner a notice. The username can be changed from `/account` (current password required; you stay signed in and a confirmed email is told). Accounts can be deleted from `/account` (password + typed DELETE): campaigns the
  user solely owns are deleted for good unless handed to a member first, and the page says so next to each one. "Download my data" on `/account` returns your account, memberships and
  the characters, factions, maps and dice rolls you made as one JSON file (never the password).
  Roles per campaign: DM (full control) and Player. Authorization is enforced on the
  server for every campaign route.
- **Characters and factions.** Profiles with class, abilities, saves, skills, speed,
  avatars, sheet images, notes (individual notes can be hidden from Players), and
  factions (many-to-many). NPC stats are hidden from Players.
  A character can keep **saved attacks** (`migrations/0032_character_attacks.sql`, up to 12): name, to-hit bonus, damage dice (e.g. `1d8+3`) and damage type, added on the edit form. The sheet shows a **To hit** and a **Damage** button for each; both roll on the server like any other roll and show to everyone in the campaign (damage never uses advantage). Attacks travel with import/export, not with campaign copies. The same Attacks list (damage type under the name, To hit and Damage buttons) shows in the character popup that opens from battle rows and map pins. Card note previews now keep a line break where the editor started a new line.
  **Hide NPCs from Players** (`migrations/0033_hide_npcs.sql`): the DM or an owner switches it on in the campaign's Settings page. While on, a Player gets no NPC card in the character list (the list page, its API and the counts on the campaign home); since DL-178 that is all it hides: NPCs still show on maps, in the battle, factions, the dice log and the activity feed, and a Player still sees a foe's numbers withheld as usual (the server filters by surface: `npcs_hidden_from_viewer('characters')`; any other call is not hidden). An NPC a Player made themselves stays visible to them, the DM sees everything, and "View as player" shows exactly what a Player gets.
  The sidebar groups its links (Table, Play, Lore, Campaign), opens with a campaign card (name, your role) and has a **Settings** link inside every campaign; on a phone Settings is in the More sheet.
  Each character keeps its stats **level by level** (`migrations/0031_character_levels.sql`): max HP, AC, the six scores, speed and the
  saving-throw and skill proficiencies are saved for the level you save the form at. On the edit form, changing Level brings back the stats saved for that level (an
  unsaved edit survives going back and forth); a level with nothing saved starts from the current numbers. The character's own
  columns are always the active level's stats, so battle, the sheet and exports keep working unchanged, and the details page
  lists the history once more than one level is saved. Not carried: import/export bundles and campaign copies hold only the
  active level.
- **Battle tracker.** Initiative, turn tracker, HP/temp HP, conditions (including
  custom ones), group colors, live sync between players. A battle log strip sits at the bottom-left of the battle page (it follows the content when the sidebar opens or closes; the closed strip shows the newest entry in its colour, and a short wash when something new lands). Opened, a small card shows the last six lines, newest at the bottom, with names, verbs and numbers styled by kind; it records damage, healing, temp HP, conditions, down / died / revived,
  rounds and arrivals, keeps the latest 50 entries per campaign, is wiped when the battle
  is cleared, and shows Players enemy events without numbers (`migrations/0026_battle_log.sql`).
  **Death saving throws** (2024 rules): a player character at 0 HP gets a "Death saves" line under its row with three pass
  and three fail pips and a "Roll death save" button. The server rolls the d20: 10+ is a success, 9 or less a failure, a
  natural 1 counts as two failures, a natural 20 puts the character back on 1 HP; three successes make it stable, three
  failures kill it. The DM can roll for any player character, a Player only for a character they made; monsters and NPCs
  never roll. Only the DM and the owner see the tally (everyone sees "Stable"). The DM's log shows every roll, Players see
  only the outcomes (stable, back on 1 HP, died). Healing, setting HP above 0 or reviving clears the tally
  (`migrations/0027_death_saves.sql`). Not included: damage taken at 0 HP does not add a failure, and there is no
  instant-death rule for massive damage.
- **Map editor.** Shapes, pins, grid setup, zoom/pan, fog of war, DM-only layers,
  token ownership (DMs assign tokens to players), familiars that sync into the
  battle, link-to-battle.
- **Dice.** Dice page and a quick-roll widget on every page, with a shared roll feed. The die drawings (shared with the corner widget) keep their numbers readable over the facet lines. Roll toasts leave after about five seconds, also in a tab that was in the background (each toast has its own deadline, swept when the tab is shown again).
- **Activity.** `/campaigns/<id>/activity` lists the latest 200 events (members joining or leaving, characters,
  factions and maps added or removed). The actor is stored as a user id, so a deleted account shows as "a former
  member". Table `campaign_activity` (migration 0025).
- **Reference (DL-127).** Nine tabs from the 2024 rules (dnd5eapi.co; a 2014 switch is described below): Spells, Monsters, Items, Conditions, Classes (with subclasses; a class shows its hit die, proficiencies, spellcasting and a level table, a subclass its features), Species (traits are fetched one by one and a missing trait only drops its own paragraph), Backgrounds, Feats and Rules (skills, ability scores, damage types, weapon properties and mastery, schools of magic, languages, alignments, poisons). Each kind is a list of API collections in `srd.KINDS`; the list shows a label under the name when a kind mixes collections (`COLL_LABEL`). `scripts/check_srd_contract.py` checks one sample of each kind nightly. Hovering (or focusing/tapping) a condition chip on the battle page, or a tile in the condition picker, shows its rule.
- **Reference outside a campaign, and the 2014 rules.** The Reference also lives at `/reference` (link "Reference" in the site header, DL-180 part 30), for any signed-in user, with the same tabs and the same endpoints under `/api/reference/` (`search`, `entry`). A 2024 / 2014 switch at the top of the page (`?edition=2014`) swaps the rulebook; the choice is kept in the session (`ref_edition`) and an unknown value falls back to 2024 in the page and is refused with "bad request" in the API. Both editions go through the same normalisers in `srd.py`; `EDITIONS` holds the per-edition labels and `KINDS_2014` the collections that differ (Species becomes Races and Subraces, there are no weapon mastery or poisons, and Rules adds the rule sections). Differences in the 2014 data are handled in the normalisers: subclass features come from `subclass_levels`, backgrounds read `starting_proficiencies` and `feature`, feats show their prerequisite, magic items pull "requires attunement" out of the first description line, and markdown marks in rule text are dropped. Cached entries are kept per edition. The monster picker on the battle page and the character form still read the 2024 Monster Manual unless the page passes `edition`. About and the credit line name SRD 5.1 for the 2014 rules (also CC BY 4.0). `scripts/check_srd_contract.py` now checks both editions.
- **Import / export** as ZIP bundles: a campaign's characters and factions (merged into a campaign you pick, from the Characters and Factions pages) and a whole campaign (exported by a DM, imported as a new campaign from the Campaigns page; see "Export and import a whole campaign" below).

## Running locally

Python 3.12 and a Postgres database are needed.

```
pip install -r requirements-dev.txt
cp .env.example .env              # set DATABASE_URL and SECRET_KEY
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=oaken postgres:16
python app.py                     # AUTO_MIGRATE=1 creates the tables
```

Open **http://127.0.0.1:5000**. Uploads go to `./uploads` locally (no Supabase needed).

## Where data lives

- **Postgres** holds characters, groups, maps, battle state and accounts. Schema changes
  are versioned in `migrations/` and applied with `python migrate.py`.
- **Uploaded images** are validated, re-encoded and stored in object storage: Supabase
  Storage in the cloud (private buckets), or `uploads/` in development. The database keeps
  only the file keys, and images are served through the app behind login.

## Upload limits

Images are re-encoded before they are stored, and what is kept is counted per user and per campaign
(table `stored_files`, module `quotas.py`). Defaults: **150 MB per user**, **300 MB per campaign**; the
existing per-file caps (avatar 8 MB, sheet 25 MB, map 30 MB, import ZIP 50 MB) still apply. Change them with
`OAKEN_QUOTA_USER_MB` and `OAKEN_QUOTA_CAMPAIGN_MB` (`0` turns a limit off). The server refuses an upload
that would pass a limit, saves nothing and shows a banner; imports are checked as a whole, so a refused
import adds nothing. Deleting or replacing an image frees its space. Images uploaded before quotas existed
count as 0 bytes until you run `python scripts/backfill_storage_usage.py` once after applying migration 0021.
The campaign settings page shows the current usage.

## Request limits

Besides the sign-in, mail and member-search throttles, signed-in changes are limited per account (counted in the
same `login_attempts` table by `security.hit`): **240 changes a minute**, **60 dice rolls a minute**, **5 new
campaigns an hour** and **25 owned campaigns** in total. A limited request gets `429` with `Retry-After`; reads are
never limited and signing out always works. Override with `WRITE_LIMIT_USER`, `DICE_LIMIT_USER`,
`CAMPAIGN_CREATE_LIMIT` and `MAX_OWNED_CAMPAIGNS`.

`/robots.txt` lets search engines see only the sign-in pages, and every page behind sign-in carries
`X-Robots-Tag: noindex`. `/.well-known/security.txt` (RFC 9116) is published once you set `SECURITY_CONTACT` to a
`mailto:` or `https://` address; until then it returns 404.

Security headers round 2 (DL-140, finished with DL-172): the Content-Security-Policy allows no inline styles at all: no `<style>` blocks and
no `style="..."` attributes (`style-src 'self'`, no `style-src-attr`). Fixed styles are classes in `static/css/style.css` (the `u-*` helpers
and a few named classes). A style that depends on data (a faction colour, the HP bar fill, where a map pin sits) is written as a `data-*`
attribute instead (`data-bg`, `data-bc`, `data-grad`, `data-p`, `data-left`, `data-top`, `data-width`, `data-height`, `data-rot`,
`data-hue`, `data-aspect`) and applied by `static/js/dyn-style.js` through the style object, which the policy allows. The script checks every
value first (hex or `var(--token)` colours, plain numbers), so text that slips into a page can never turn into arbitrary CSS, and it
handles new nodes as the battle and map screens redraw. `tests/test_no_inline_styles.py` fails if a template or script writes a
`style=` attribute; `tests/test_e2e_csp_styles.py` opens the main screens in a browser and fails on any policy violation. Elements that
start hidden use the `hidden` attribute (the scripts that show them set `.hidden`, not `style.display`). Responses also carry
`Cross-Origin-Resource-Policy: same-origin`, and the policy has `report-uri /csp-report`: a browser that blocks something posts there and
the app logs one `csp violation: ...` warning line (nothing is stored; the endpoint needs no sign-in). HSTS `preload` still waits for the
final domain (DL-134).

## Database housekeeping

Foreign keys that child tables are looked up by carry covering indexes (`migrations/0028_fk_indexes.sql`, from the Supabase
performance advisor). Tables that only grow are bounded without a cron job: `login_attempts` (24 h), `campaign_activity`
(200 per campaign), `dice_rolls` and `battle_log` (per campaign) and `notifications` (200 per user, pruned when a new one
arrives). The advisor's "RLS enabled, no policy" notices are intentional: every table is deny-all and the server uses the
service role, so do not add policies to "fix" them.

## Backups

Supabase's own backups do not cover uploaded images (and the Free plan has none at all), so the repo ships its
own: `python scripts/backup.py` saves the database and every image, and `python scripts/restore_drill.py <backup>`
proves the backup restores into a throw-away database and that the app runs on it. Full routine, recovery steps,
targets and the drill log: [BACKUPS.md](BACKUPS.md).

## Monitoring and troubleshooting

- **`/healthz`** (public) reports whether the database, schema and storage are ready
  (HTTP 200, or 503 with a short hint). It never exposes connection strings.
- **Logs.** On Vercel the app writes one JSON object per line (`LOG_FORMAT=text` for plain
  lines locally, `LOG_LEVEL` to change verbosity). Every request has an `X-Request-ID`
  (also in the response headers) and one access line with method, route, status, duration
  and user id. Query strings are never logged.
- **Errors.** An unexpected server error shows the user a generic message and a reference
  (the request id). Search the logs for that id to find the stack trace.
- **JSON error shape.** Every AJAX/JSON route (anything under `/api/`, JSON requests, `/uploads/sign`)
  answers failures as `{"error": "<message for people>", "code": "<stable slug>", "request_id": "..."}`
  with the matching HTTP status (401 also carries `login_url`; quota errors carry `scope`). Build
  them with `api_error()` in `app.py`. In the browser `static/js/api.js` (`OakenApi`) turns them into a toast.
- **Error tracking (optional).** Set `SENTRY_DSN` and add `sentry-sdk` to
  `requirements.in` (then recompile the lock file). Without both, nothing is sent. Personal
  data is not sent.

## CSS conventions

Layout CSS uses logical properties (`margin-inline-start`, `inset-inline-end`, `border-inline-start`,
`text-align: start`) instead of left/right, so a right-to-left language (Persian, say) can be added later without
rewriting the stylesheet. A deliberate physical `left`/`right` (centering with `translate`, map canvas coordinates)
carries a `/* phys */` marker; `tests/test_css_logical.py` fails on any unmarked one. Translating the interface is a
separate decision (only worth it if players read Persian).

Native form controls are themed in one block at the end of `style.css` (DL-154): checkboxes, radios and range sliders are
drawn in brass (light and dark theme) instead of browser blue, with a visible empty-box border (3:1 or better), press
feedback, and larger targets on touch screens. Controls that already have their own look (toggle switch, access cards,
faction chips, skill tri-state, saving-throw pip, dice roll-mode) are excluded in that block's selectors; a new custom
control that hides its `<input>` needs adding to the same `:not(:is(...))` list.

Each campaign opens on an Overview page (DL-144, `campaign_home`): the campaign image and bio, count tiles, the player list (DM or Player), the party, the running battle, the latest dice rolls
and recent activity. It reuses the Battle, dice and Activity queries, so NPC hiding and enemy redaction apply to it unchanged. A
"next session" card is left for DL-152.

The campaign bio is stored in the same format as character notes (a JSON list of sanitised bold/italic/bullet HTML boxes in
`campaigns.description`; old plain-text bios still read fine) and the campaign notes in `campaigns.notes` (migration 0034). Long text on
Overview folds behind "Read more" (`static/js/home.js`). A character can be attached to a member (`characters.player_id`, set by the DM or an
owner from Settings > Members): `owns_character()` then lets that member edit it, read its hidden notes and make death saves, and map
tokens of that character are theirs to move (`_may_move_pin`). Deleting stays with the creator and the owners.

Print sheet (character page, DL-157): a button that opens the browser's print window, where "Save as PDF" also works. A print stylesheet
leaves out the menus, buttons, dice, roll controls and the sheet viewer, drops the cards onto white, and the page switches to the light theme
for the print only. A character whose stats are hidden from the viewer has no button.

Quests (DL-151, migration 0038): a card on the campaign Overview page. The DM adds a quest (title, what the players know, optionally hidden),
marks it done or reopens it, edits its title and details (the same limits as adding, and editing never changes whether it is hidden), hides it from or shows it to Players, or deletes it; Players read the quests that are not hidden. Up to 60
per campaign. Adding or finishing a visible quest shows up in the activity feed. Not built: objectives inside a quest, quest export.
The quest buttons (mark done or reopen, hide or show, delete, edit) are icon-only; each has a title and an accessible name that includes the quest.
On the Overview, the whole party tile opens the character page, avatar included (the avatar preview stays on the Characters list and the character page). On the Characters list the name on a card is a link to the character page too.

Session scheduling (DL-152, migration 0035): the DM or an owner sets one "next session" per campaign from the Overview (`campaigns.next_session_at`
in UTC plus a short note). The browser shows it in each viewer's own time zone (`static/js/home.js`); members answer Going / Maybe /
Can't (`session_rsvps`); a new time clears the answers and sends members a notification and an activity entry; `/session.ics` gives a
calendar file. A session more than six hours past is treated as none. A timed reminder is not built (needs a scheduler).

Roll Initiative (battle page) opens a small menu on hover or focus (a tap on a phone): everyone, the player characters or the NPCs and
monsters. `POST /api/battle/roll-initiative` takes `{"scope": "all" | "pc" | "npc"}`; the others keep their numbers.

Long Rest (battle page, DM only; DL-149): every player character goes to full HP, loses temporary HP, and has death saves cleared and
Rest (battle page, DM only): one dropdown button holds Short rest and Long rest. Short rest: a dialog lists each living player character; the DM types how many HP each regains (capped at max HP), death saves are cleared, and one line goes in the battle log. The battle menu no longer has a Create Character button.
is_dead reset; conditions, NPCs and monsters are left alone, and the battle log gets one line. `POST /api/battle/long-rest` takes an
optional `{"id": <participant id>}` to rest one character. Short rest and hit dice are not built (the sheet has no hit dice yet).

Visual round 3 (DL-155): a campaign without an image gets a generated cover (a hue from its id, with its initials);
a character without a portrait shows its class art, else its initial; character cards show a live HP bar and conditions for
anyone in the running battle (`_battle_live_status`, built on `_battle_rows`, so a Player gets no monster numbers); empty states sit in a brass medallion.

## Colour contrast

Both themes pass an axe-core `color-contrast` audit (WCAG AA, 0 violations across the main pages). Convention in `static/css/style.css`: use the `-ink` tokens (`--brass-ink`, `--moss-ink`, `--blood-ink`) for text, never the raw fill colours, and `--on-brass` for text on a solid `--brass` fill.

### NPC allies
An NPC can be marked **Ally** on the character form (the switch is greyed out until NPC is on). An ally is still an NPC (NPC tag, DM-only dice, NPC initiative scope), but Players see its stats and it stays visible in the character list when "Hide NPCs" is on. Migration `0036_npc_ally.sql`.

A monster from the manual (New character, or the Battle "Add monster" menu) also fills the Attacks card: every action with a to-hit bonus becomes an attack with its first damage roll and type. Extra riders (e.g. "+1d4 with advantage") stay in the stat-block note, and dice the card cannot hold are listed without a damage roll.

### Map ruler (DL-153, first slice)
Each map has a **Feet per square** setting (grid settings, default 5, 1-100; migration `0037_map_feet_per_square.sql`). The **Ruler** tool (next to Reset Zoom, works for Players on a locked map too) measures a drag in squares and feet, counting a diagonal step as one square like 5e does, and reads the result out in a live region. The line is local to each person and is cleared by Esc or another tool.

### Sign-up, login and Google (DL-158)
Sign-up needs a username, an **email** and a password. The email is stored unconfirmed and a confirmation link is mailed when mail is set up (it never blocks sign-up; accounts made before this rule get a banner until they add one). The login box takes a **username or an email**; if several accounts typed the same unconfirmed address and none confirmed it, email login is refused for it (the username still works). Pages: `templates/auth_base.html`, `static/css/auth.css`, `static/js/auth.js`.

**Sign in with Google** is an OAuth code flow with PKCE and a state check (`/auth/google`, `/auth/google/callback`). It stays hidden until `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set; set `GOOGLE_REDIRECT_URI` only if the callback URL cannot be worked out from the request. In Google Cloud Console create a Web application OAuth client and add `https://<domain>/auth/google/callback` as an authorized redirect URI. Google must report a verified email. The same confirmed email links to the existing account; an unconfirmed address typed on another account is never linked and is cleared. A Google account has no password until the person adds one under Account (renaming and deleting work without one).

### Profiles (DL-97, first step; migration `0039_profiles_and_google.sql`)
`/u/<username>` shows avatar, name, bio, member-since and up to 6 featured player characters (name, class, level, portrait only; never the campaign, stats or notes). Under Account the owner picks who can open it: everyone signed in, people who share a campaign (default), or only themselves. A profile you may not open answers 404, the same as a name that does not exist. Campaign Home links player names to their profiles unless private.

### Account settings sections (DL-39)
`/account` is split into five sections with a side menu (a row of chips on a phone): **Profile**, **Privacy** (who can open your profile page, featured characters), **Sign-in and security** (email, username, password, sign out everywhere), **Appearance** (dark, light or match the device; saved in this browser under `oaken-theme`, value `system` is read by the head script of every page) and **Your data** (download, delete). Without JavaScript every section shows. A link such as `/account#email-panel`, an error banner or a `?mail=` result opens the section it belongs to; otherwise the last section is remembered for the tab. Notification settings are not part of this yet because there are no notification preferences to set. Script: `static/js/account.js`.

### Party treasury (DL-148; migration `0040_treasury.sql`)
The Treasury page (`/campaigns/<id>/treasury`, sidebar under Table) is the party purse. The purse is not stored: it is the sum of the entries in `treasury_entries`, each holding a signed change per coin (cp, sp, ep, gp, pp), who made it, an optional character it was for, and a note. Any member can add coins, spend coins, or split coins; the DM can remove any entry and a member their own. Spending pays the coins named first, makes up any shortfall from the smallest coins, and gives change back (pp, gp, sp, cp), so the purse never goes below zero in any coin; removing an entry is refused when later entries already spent its coins. Values are worked in copper (cp 1, sp 10, ep 50, gp 100, pp 1000). "Split evenly" shares typed coins, or the whole purse when none are typed, between the chosen player characters: each gets the same share rounded down, the rest stays in the purse, and it is recorded as one spending entry. Entries show in the campaign Activity feed. Not built: links to the item manual (DL-114) and inventory (DL-119).

### Treasury follow-up: character purses (DL-148; migration `0043_treasury_purses.sql`)
Every player character now has a purse of its own next to the party purse. An entry belongs to exactly one purse: `treasury_entries.character_id` NULL is the party's, a character id is that character's (entries that already named a character now count in that character's purse). The Treasury page shows the party purse, a "Character purses" list (coins, total, links to the profile and to that purse's history), the **Add or spend** form (choose whose purse) and **Share or hand over** (take coins from one purse and split them evenly between any purses, or hand them to one; no amount means the whole purse; what does not divide stays behind). The entries of one share carry the same `batch` and are removed together. Anyone may use the party purse; a character's purse is for the DM and whoever made or plays the character. Each player character's profile has a Purse section (coins, last entries, links). Deleting a character returns its coins to the party purse. The page opens with a short "How the treasury works" guide. Coins show as a small coin icon in each coin's colour; mistakes (no recipient ticked, no amount) are explained on the page instead of a bare error.


### Treasury page flow (DL-148 follow-up)

The purse figure in gold (for example "worth 190 gp") counts every coin in that purse as gold (1 pp = 10 gp, 1 ep = 0.5 gp, 1 sp = 0.1 gp, 1 cp = 0.01 gp), so 40 gp and 15 pp show as 190 gp; the coin chips beside it are the raw coins. ### Your characters (DL-160; migrations `0045_character_library.sql`, `0046_your_characters_wording.sql`)

### Map and battle sync is idempotent (DL-11, DL-175)

The rule: while a map is linked to the battle, a character token and a battle row are tied together by `map_pins.participant_id`, and a unique index on `(map_id, participant_id)` allows at most one token per row. `_reconcile_map_battle` runs on every map refresh and only fills gaps (a row without a token gets one, a token without a row adopts an unplaced row of the same character or makes one, a token whose row is gone is removed), so running it again changes nothing. Familiar props are the one-way case: placing one on a linked map creates its temporary row, and deleting the pin removes it. The code already worked this way; `tests/test_map_battle_idempotent.py` now proves it: repeated refreshes, six clients linking and refreshing at the same moment, and link/unlink/link cycles all end with exactly one row and one token per character.

### Oaken visual identity: a quiet lift on hover (DL-180, part 11, replaces the burn)
The hover burn (DL-180 parts 5 and 7, a scorch drawn in CSS along a panel's edge) is gone. It was on 35 panels, most of which cannot be clicked, and it read as heavy. Now only paper cards that are things to open respond to the pointer, and they all respond the same way: the card rises 2px, its shadow deepens and a hairline ring draws in. Nothing else on the card moves. Panels you do not click (the Overview cards, the sign-in card, the legal sheets, the empty states, the character summary and notes, the dice stage) have no hover at all, because a hover on something that does nothing promises a click that never comes.

- **Which cards.** `.o-lift`, set next to `o-paper` on the character dossier (`characters_list.html`), the library card (`library.html`), the faction card (`groups_list.html`), the campaign card (`campaigns_list.html`), the map card (`maps_list.html`) and the journal session row (`journal.html`). A new clickable paper card opts in by adding the class.
- **How it works.** One rule set in `static/css/oaken.css`, `.o-paper.o-lift`. At rest the card keeps the normal `--paper-shadow`. On hover it takes `translateY(-2px)` and `--paper-shadow-lift` (the same shadow, deeper, plus a 1px ring in `--paper-lift-ring`: antique brass on the dark theme, where the paper's brown line would vanish against the page, and the paper's own line on the light theme; one token pair per theme), and its border fades to transparent so the ring replaces the border instead of doubling it.
- **Timing.** 180 ms with `--ease-out` (`cubic-bezier(0.23, 1, 0.32, 1)`, new on `:root`) on transform, box-shadow and border-colour. These are transitions, not keyframes, so a pointer that leaves half-way turns the card round from where it is instead of jumping (checked: at 70 ms the card was at -1.8px, and it returned to 0 after leaving).
- **When it shows.** The movement only on a mouse or trackpad (`@media (hover: hover) and (pointer: fine)`). Keyboard focus anywhere inside the card (`:has(:focus-visible)`) shows the ring and shadow without any movement, because focus is a state and not an invitation. A touch screen shows nothing. With `prefers-reduced-motion` the card never moves and only the shadow and ring change.
- **Removed.** `.o-burn`, `.o-burn--soft`, the `::before` and `::after` scorch layers, the two noise SVGs (`--burn-noise-soft`, `--burn-noise-char`), the `--burn-stain`, `--burn-scorch`, `--burn-char` and `--burn-on` tokens, and their print and `prefers-contrast` rules, about 90 lines in `oaken.css`. The class is gone from all 35 places in 21 templates. In `style.css` the separate hover rules of the dossier, faction, map and journal cards (each had its own distance, ring and timing: a 2px lift on three of them, 1px on the journal) were deleted in favour of the shared one.
- **What did not change.** Layout, text, controls and every route. The rest state of 17 pages in both themes (34 full-page screenshots at 1440px) was compared with the state before this change: identical, apart from a faint difference in the shadow between stacked panels (largest change 54 of 255, in the dark gap between the Overview cards), caused by the panels no longer forming their own stacking layer.
- **Tuning.** Distance: `translateY(-2px)`. Depth and ring: `--paper-shadow-lift` in the two theme blocks. Speed and curve: the `transition` on `.o-paper.o-lift` and `--ease-out`.
- **Tests.** `tests/test_card_hover.py` (17): no template, script or style sheet mentions the burn; each of the six cards carries `o-lift`; the movement sits inside the hover media query and nowhere else; the transition uses `--ease-out` and stays under 300 ms; and, in a real browser, a hovered card moves -2px and shows the ring, the card stays still with reduced motion and on a touch screen, and keyboard focus rings without moving.
- **Not done.** Checked in Chromium only (desktop mouse, emulated phone, reduced motion); not in Firefox, Safari or on a real device. In a browser without `:has()` the card ring does not show on keyboard focus, but the focused control still has its own focus ring. The library card was checked in the stylesheet and test only: the tutorial account has no library entries to hover.

### Avatars and campaign pictures are kept by the browser (DL-180, part 29)

Stored images were already sent with `Cache-Control: private, max-age=31536000, immutable`, yet browsers fetched them again on every page. The cause was two other headers on the same response: Flask marks any response that read the session `Vary: Cookie`, and the signed-in session cookie is signed again on every response, so its value was different every time. A browser that honours `Vary: Cookie` (Safari and Firefox do; Chrome effectively ignores it) saw a different "variant" on each visit and never reused its copy.

- **Fix.** `_OakenSessionInterface` in `app.py` leaves the response alone on the two image routes (`uploaded_file`, and `map_image`, which the browser re-checks by ETag so the fog is always current): no `Vary: Cookie`, no new `Set-Cookie`. A stored image is the same for everyone who may see it, under a key nobody can guess, and the response is still `private`.
- **A write that was not needed.** `campaign_access_required` set `session['last_campaign_id']` on every request, which marks the session modified and re-signs the cookie even when the value had not changed. It is now written only when it changes, so campaign pages and the map picture stop re-signing the cookie for nothing.
- **Unchanged.** Signed-out visitors are still turned away from `/uploads/...`; ordinary pages still keep the session alive; the map picture is still re-checked by ETag on every load (a small 304, not a download).
- **Tests.** `tests/test_csrf_sessions_headers.py` (no `Vary` and no cookie on the image responses, a 304 for the map picture, pages still refresh the session) and `tests/test_e2e_image_cache.py` (in Chrome, a reload and a visit to another page show avatars from the browser cache; this guards the policy, it cannot reproduce the Safari and Firefox problem).

### Pointer: more pop, a longer trail, true movement (DL-180, part 28)

- **Pop.** The dot is 14 px with a bright core fading into the person's colour and a wider, layered glow (still no ring, no name). It pops in with a small overshoot (260 ms, ease with a slight spring) and shrinks away as before.
- **Trail.** Longer (150 px at full speed) and brighter, and it now follows the speed over about 170 ms instead of 60 ms, so the blur builds and fades more slowly. It starts at a lower speed (40 px/s), so slow movements show it too. With reduced motion there is still no trail.
- **Other people see the real movement.** Unlike tokens, which glide, the pointer is no longer eased for other people: it is sent 20 times a second (`EVERY.ptr = 50` ms in `map-live.js`; other kinds stay at 10 a second) and drawn only about 65 ms behind real time (a little over one message interval), joined straight from position to position, so the path they see is the path that was taken. The cost is Realtime traffic: one person pointing is 20 messages a second.
- **Tests.** `tests/test_e2e_map_pointer.py` (the sender cap is now 20 a second).

### Pictures on the canvas, beside the map (DL-180, part 27)

An additional image used to be a shape inside the map. It is now part of the canvas: it sits beside the map and the canvas grows to hold it. Migration-free: a picture is still a `map_drawings` row of kind `image`, so every picture already placed keeps its place.

- **Where it lands.** `POST .../api/maps/<id>/images` stores the file as before and the server chooses the place: to the right of everything on the canvas, top-aligned with the map, then to the left, below, above if there is no room on the right (`_place_beside_map`). It never overlaps the map or another picture while there is room. When the map snaps to the grid, the picture's corner lands on a grid line. A picture is shrunk to at most the size of the map each way, never enlarged. The client no longer sends a position.
- **Settings.** Only position (drag), size (corner handles, which keep the proportions), turn (the turn handle) and remove. No colour, fill, lock, hide-from-players or attach: the buttons are hidden for a picture (`.pin-action-bubble.is-picture`) and the style panel does not open for it. The whole table sees every picture; an older picture that had been hidden is shown (`_PLAYER_SEES`).
- **The canvas world.** Coordinates are still map pixels with the origin at the map's top left. `world` in `map.js` is the box that holds the map and every picture (left and top can be negative), and `#map-canvas` and `#ruler-canvas` are sized and placed to cover it (`layoutWorld`, `.on-world`). With no pictures the world is exactly the map and nothing changes: same canvas size, same stylesheet layout. A picture may reach 1.5 map sizes past an edge and be at most two map sizes across (`_clamp_image_box` on the server, `limitImage` in the script), so the canvas is at most four map sizes across. A world larger than 16 million pixels is drawn at a lower resolution (`worldScale`). While a picture is being dragged the world only grows, and tightens again a moment after the hand lets go. Each picture has room round it for its handles.
- **Follows the canvas settings.** The grid is drawn over the whole canvas, pictures included (`drawGridOnto` takes the area to cover). Pictures are drawn under the grid and under every drawing; the map's own picture is under them. With "snap to grid" on, a moved picture's corner meets a grid line, and the corner of an upright picture that is being resized does too. Tokens, drawings, the ruler and its templates, and the right-click pointer all work on the extra canvas (the pointer module takes an optional `bounds`). Fog of war still covers only the map.
- **Picking.** A drawing on top of a picture is picked first (`topFirst`); the picture is picked when nothing else is under the pointer.
- **View.** After a picture is added, and when a map with pictures opens, the view pulls back to hold the whole canvas, with a little room around it (`fitView`); "Reset zoom" does the same. A map with no pictures keeps the plain 100% view.
- **Undo, export, import.** Unchanged: delete and move are undoable; pictures travel in a campaign export as before. A picture put back by undo is held to the same limits.
- **Tests.** `tests/test_map_images.py` (placement, grid, limits, no hiding) and `tests/test_e2e_map_images.py` (canvas growth and shrink, grid over the picture, snap, proportions, turn, menu, pointer, Player view).

### Oaken visual identity: one type scale (DL-180, part 12)
The three typefaces were already right (Fraunces for headings, Inter for body and interface, IBM Plex Mono for numbers and metadata, all self-hosted in `static/fonts/` with their licence text), and every page rendered in them. What was missing was a scale: the style sheets set text in 30 different pixel sizes, many only half a pixel apart (8.75, 9, 9.5, 10, 10.5, 11, 11.5, 12, 12.5...), 58 of the text styles on the audited pages were under 11px, and nothing named a size. Now there are 11 size tokens in `static/css/oaken.css` (section 4) and `style.css`, `auth.css` and `public.css` use only those.

| Token | Size | Used for |
| --- | --- | --- |
| `--fs-2xs` | 10px | uppercase mono labels, phone tab labels, tiny tags |
| `--fs-xs` | 11px | meta lines, chips, captions |
| `--fs-sm` | 12px | secondary text, table cells, small buttons |
| `--fs-md` | 13px | compact body, controls, list rows |
| `--fs-base` | 14px | body text, navigation, form labels |
| `--fs-lg` | 16px | emphasised and reading text, form fields on a phone |
| `--fs-xl` | 18px | card and dialog titles |
| `--fs-2xl` | 20px | section headings, large numerals |
| `--fs-3xl` | 24px | phone page titles, vital numbers |
| `--fs-4xl` | 28px | page titles |
| `--fs-5xl` | 34px | the big result of a roll |

- **How the old sizes were mapped.** Each went to the nearest step, ties upward (so 10.5 became 11, 12.5 became 13, 13.5 became 14), with four exceptions chosen so titles and numerals do not grow: 19px card titles became 18 (not 20), 26px titles and numerals became 24, and 30px became 28. The phone tab-bar labels and the phone battle buttons stay at 10 (they were 10.5 and would not fit at 11). The character name in a battle row (`.battle-name`, was 15px) stays at 14, because 16 makes the compact row taller than the 62px that `tests/test_e2e_battle_rows.py` allows. In practice body and label text is up to half a pixel larger, nothing is more than 2px different, and no size set in the style sheets is under 10px any more (a few `<small>` elements, which are sized relative to their parent, still render at 9 to 11px, and the dice SVG numbers are drawn in the dice's own units).
- **What was left alone.** Fluid display type (`clamp()` on the Overview name, profile name and the public pages' titles), the 60px and 76px roll totals, the landing page (its own rem and `clamp()` sizes), `<small>` elements and `0.7em` on the pin chip (relative to their parent), and the SVG numbers in the dice art.
- **How it was checked.** Before and after screenshots of 17 pages in both themes at 1440 and 390px. A script that counts the lines of every text element on 22 pages at 360, 390, 820 and 1440px, before and after: no page scrolls sideways that did not before, nothing new is cut off with an ellipsis, and 10 long paragraphs gain one line because their text is a little larger. It found two real problems that were fixed: the phone tab label "Your characters" was cut off and the phone battle button "Add Character" wrapped onto two lines.
- **Tests.** `tests/test_type_scale.py` (11): the scale is defined once and ascends; no style sheet sets a text size in loose pixels (display type of 40px and up and the dice SVG are the only exceptions); every token used exists; every page that loads one of the sheets also loads `oaken.css`; and in a real browser the rendered text of 11 app pages (at 390 and 1440px) and 6 public pages uses only the scale (display type and `<small>` excepted). The tests fail on the old style sheets.
- **Not done.** The symbols `●`, `○` and `◆` (the skill marks) and `✓` are not in the self-hosted font subsets, so each system draws them in its own symbol font; replacing them with drawn shapes would touch five templates and a script, so it was left. The landing page's own sizes were not folded into the scale. Chromium only.

### Oaken visual identity: error page, sign-in controls and empty states (DL-182, part 9)
Three things that were still in the old look. Routes, permissions and workflows are unchanged; the only logic change is which page an error request gets.

- **An Oaken error page.** A request that cannot be answered used to end on Flask's grey default page (a 404 or 405) or on bare text (an expired form, too many requests, a file too large, storage down). `templates/error.html` is now the page for all of them: the public frame (so the header shows the signed-in or signed-out menu), a hero line on the left and a paper card in the oak frame on the right, with the status, a title, what happened and where to go next ("Go to your campaigns" and "Home" when signed in; "Back to home" and "Log in" when signed out). `ERROR_PAGES` in `app.py` holds the wording for 400, 403, 404, 405, 413, 429, 500 and 503; any other client error uses the 400 text and any other server error the 500 text. A 429 with a `Retry-After` header also says "You can try again in about N seconds." The message is escaped by Jinja like everything else.
- **Who gets the page.** `http_error` (the handler for every `HTTPException`: unknown address, wrong method, `abort(...)`, an unhandled exception as a 500) renders it for every non-JSON request. Routes that used to answer in plain text (`_reject_request`, `limit_writes`, the campaign-creation limit, `quota_exceeded`, `storage_unavailable`) go through `_plain_error`: the page when the request is a navigation, `text/plain` as before otherwise. A navigation is `_is_navigation()`: not a JSON or `/api/` request, and the best type the client accepts is `text/html`, which is what a browser page load or form post sends. `fetch`/XHR (`*/*`) and bare clients such as curl or the tests keep their plain text, and JSON routes keep the `{error, code, request_id}` shape. Status codes and headers (`Allow`, `Retry-After`) are kept. If drawing the page fails, `error_page` logs it and returns `None`, and the caller falls back to the plain answer, so an error is never turned into two.
- **Sign-in, sign-up, forgot and reset cards.** These cards are paper, but their error box, hints and links were written for the dark card (pale red, pale green, bright brass) and measured about 2:1 on tan. Inside `.o-paper` they now use the ink tones the rest of the paper uses: error and note boxes, the "is-bad" and "is-good" hints, a red border on an invalid field, brass-ink links, and links underlined so they do not depend on colour alone. The block is "Sign-in cards, the error page and empty states on paper (DL-182 part 9)" at the end of `style.css`.
- **Empty states.** The Characters list and the Battle page showed their "nothing here yet" message in a dashed box. They are now a paper panel (`empty-state o-paper`) like the other cards. The other empty states already sat on paper (campaign home cards, lists and the ledger pages).
- **Loading states.** The app has few: the button spinner on sign-in (`.is-loading`), the upload ring and the "Loading…" lines in Reference. They were checked in both themes and needed no change.
- **Contrast.** Measured against rendered pixels, text rectangles only, in both themes (desktop): login, login with an error, register, register with errors, forgot password, a bad reset link, the 404 page signed out and signed in, the 405 page, and the Characters and Battle empty states. All 4.5:1 or better. The error box text is a fixed `#7a2620` on an 8% red tint: the theme's blood ink measured 4.3:1 on the darker paper of the dark theme.
- **Tests.** `tests/test_error_pages.py`: the 404 page signed out and in, a stranger's campaign page, a 405 keeping `Allow`, JSON routes unchanged, an expired form (page, plain text and JSON), `Retry-After` and the wait sentence, escaping, the generic wording, the 500 page, and the fallback when the template cannot be drawn.
- **Not done.** The responsive and accessibility pass, the consistency pass, and a closing animation for dialogs (the rest of the redesign list).

### Export and import a whole campaign (DL-183)
A DM can export everything they built in a campaign as one ZIP, and anyone can import such a file as a brand-new campaign. This is separate from the older export and import on the Characters and Factions pages, which stay as they were (they move characters and factions between campaigns, and a whole-campaign file is refused there with a message that points at the Campaigns page).

- **Where.** Export: the settings page of a campaign ("Back up or move this campaign", DMs only) and an export icon on each campaign card in the Campaigns list (campaigns where you are a DM). Import: "Import a campaign" at the top of the Campaigns list. Routes: `GET /campaigns/<id>/export/campaign` (campaign access and DM required, so "view as player" is refused too) and `POST /campaigns/import` (any signed-in account). No migration: the import only writes to tables that already exist.
- **What is in the file.** `manifest.json` (`format` `oaken-campaign`, `version` 2) plus `images/<avatars|sheets|maps>/...`. It holds the campaign (name, description, setting, status, "hide NPCs", notes, banner), factions, characters and NPCs (stats, class, proficiencies, notes including the DM's hidden notes, saved attacks, level history, avatar, sheets, faction memberships with the main faction first), maps (picture, grid settings, locked-for-players, fog, tokens, props, drawings and which token a drawing is attached to), quests (including hidden ones), the session journal and the treasury (every entry, with the character purse it belongs to).
- **What is left out on purpose.** People and history: members and who plays which character, invitations and invite links, the activity feed, dice rolls, notifications, session RSVPs and the next-session note, the live battle, the short-lived map measures, temporary familiars, and the campaign's access mode. Because the file carries hidden notes, hidden quests and DM-only tokens, only a DM can export it; the settings page says to keep the file to yourself.
- **Import always makes a new campaign.** The person importing becomes its owner and DM, the access mode is Private, nothing is merged into an existing campaign, and importing the same file twice gives two separate campaigns. Characters are unassigned (nobody plays them until the new DM assigns them).
- **How the file is read.** Same envelope checks as the characters import (`importer.open_zip`: ZIP only, 50 MB, 3000 entries, 300 MB unpacked, no path tricks), with a larger manifest allowance (24 MB). `campaign_transfer.normalize_manifest` then turns the manifest into clean data: types are coerced, numbers must be finite and are clamped, text is capped and stripped of control characters, rich text goes through the same sanitisers as the forms, colours must be `#rrggbb`, map icons and classes must be known, drawing geometry keeps only the keys the map editor writes, and quests, journal and treasury entries are capped at the forms' own limits (`CAMPAIGN_TRANSFER_LIMITS` in `app.py`). Items that point at each other use `ref` numbers that only mean something inside the file; every one becomes a new row, so nothing can reach into another campaign. A token whose character is not in the file, an unknown icon or a duplicate ref is dropped, not fatal.
- **Images** go through the normal upload pipeline again: validated, re-encoded (so a repeated export and import can soften an image slightly), stored under fresh keys (two uses of one image never share a file), counted against the quotas as a whole (`quotas.check` before anything is uploaded; over the limit imports nothing), and uploaded before the commit, so a storage failure rolls the whole import back. A picture that is missing or unusable from the file never blocks the import: a map keeps its tokens on a blank canvas of the same size, a character just has no picture. At most 400 images are read from one file.
- **Same gates as New campaign.** `_campaign_create_block` (shared with `campaign_new`) applies the owned-campaign cap (25) and the creation rate limit, and the usual confirm and CSRF checks apply. Large files arrive through the same direct-upload path as other imports (`import_file` input).
- **Size.** The export is refused with a banner on the settings page if the finished ZIP would pass 50 MB, because the import would turn it away and temporary storage could not hold it.
- **Tests.** `tests/test_campaign_transfer.py` (round trip with maps, fog, tokens, drawings, quests, journal and treasury; the DM-only rule; privacy of the file; hostile and broken files; limits; direct upload; the pages). `tests/test_authz_roles.py` lists the two routes.

### Tutorial campaign for every account (DL-184)
Every account has its own copy of the DM's Tutorial campaign in its campaign list, and is its owner and DM. It is a normal campaign: the account can play with it, change it or delete it.

- **Where it lives.** `tutorial/tutorial-campaign.zip` is the whole-campaign export the DM made (a faction, four heroes, two goblins, a map, a quest and four starting purses), kept exactly as exported. To change the tutorial for everyone who has not had it yet, export the updated campaign from Oaken and replace that file (same name). Accounts that already have their copy keep what they have.
- **When an account gets it.** The first time it opens its campaign list (`campaigns_list` calls `give_tutorial_campaign`). That covers new accounts, which land on the list right after sign-up, and every account that existed before this change, which gets it on its next visit. The copy took 0.15 to 0.2 s extra on a development machine with local file storage (the pictures are decoded once per process, so only the first copy after a cold start is slower; on Supabase it also uploads 13 pictures); after that the list costs one extra small query.
- **Only once.** Migration `0059_tutorial_campaign.sql` adds `users.tutorial_campaign_at`, empty until the copy is made. The flag is set in the same transaction as the copy, so a failed copy leaves the account unclaimed and the next visit tries again, and two requests at once make one copy (the second waits on the row, then finds it claimed). Deleting the tutorial does not bring it back. Until the migration is applied the list works as before (the missing column is logged).
- **How the copy is made.** With the same code as "Import a campaign" (`_import_campaign`), so the account is the owner and DM, the access mode is Private, and every picture is stored under a fresh key for that account (deleting one account's tutorial never breaks another's). It differs in three ways: it does not use the campaign-creation rate limit or the owned-campaign cap check, it is not turned away by the image storage limit (the pictures are still recorded against the account's usage, about 2.3 MB), and the treasury entries are dated when the copy is made. The file and its decoded pictures are read once per process.
- **No records or logs.** An export carries no activity feed, dice rolls, battle log, invitations, members, notifications or RSVPs, and the copy adds none, so all of them start empty. The four 50 gp "Income" entries (one starting purse per hero) are the only records it holds. The journal is empty.
- **If it fails.** A missing or unreadable file, or a storage error, is logged and never reaches the person: the list still opens. This process then leaves that account alone for 5 minutes (`TUTORIAL_RETRY_SECONDS`) so a storage outage does not slow every page load.
- **Storage cost.** Each account stores its own pictures: about 2.3 MB per account (13 images), so 100 accounts use about 230 MB of Supabase storage. Sharing one set of files between accounts would save that, but the app deletes a campaign's files when the campaign goes, so every copy owns its files on purpose.
- **Switch.** `OAKEN_TUTORIAL_CAMPAIGN=0` turns the whole thing off (the test suite sets it so tests that count campaigns are unaffected; `tests/test_tutorial_campaign.py` switches it on for itself).
- **Tests.** `tests/test_tutorial_campaign.py`: owner and DM, what the copy holds, no logs and fresh dates, once and not again after deleting, separate files per account, over the storage limit, no use of the creation allowance, the switch, a missing file, a failed copy retried later, and three visits at once making one copy.
